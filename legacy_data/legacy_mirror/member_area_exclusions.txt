# Mirror-crawler content exclusions: legacy member-account surfaces.
# One site-root-relative URL path per line, percent-decoded; an entry matches
# itself and everything beneath it. Consumed by create_mirror_footbag_org.py
# --exclusion-list, which is repeatable: pass this list AND the generated
# committee-scoped one. Hand-maintained, and deliberately separate from that
# one because it is regenerated wholesale and would wipe these entries.
#
# Why these are excluded. Each is one of three things, and none has archival
# value. The signed-in dashboard, both join pages, the profile editor, the
# problem-report form, the event registration forms and the player registration
# summary render the crawling account's own private data back to it: an e-mail
# address on all of them, and on the registration surfaces the postal address as
# well, alongside membership tier and tournament history. Note the address they
# echo is the one the member registered with, which need not be the one being
# signed in with, so the content guard below is not a substitute for listing
# them. The member directory result page and the per-event registered-player
# roster are lists of OTHER people, frozen in time, carrying the contact details
# the legacy site showed only to administrators. Everything else is a form whose
# backend stops existing at shutdown, so its submit button can never do anything.
#
# The event registration SUMMARIES (registration/regsummary) are a different
# surface and stay: they are the archival record of who competed, and they
# carry no contact data. Its two neighbours do carry it and go: the per-event
# roster lists every registered player's e-mail address, and the per-player
# summary is one account's own registration record, e-mail and address included.
#
# What is deliberately NOT here, and must never be added:
#
#   members/profile      The part of the member section with real archival
#   members2/profile     value. Kept reachable by id and by links from club,
#                        roster and gallery pages. Listing bare 'members' or
#                        'members2' would match these too, via the ancestor
#                        walk, and destroy every captured profile.
#
#   members/html         The member-section stylesheets. Excluding them leaves
#   members2/html        every surviving member page unstyled.
#
#   members/home         These three carry the signed-in dashboard and are
#   members2/home        replaced in place by the static member-area notice,
#   members2 (landing)   not deleted. An exclusion entry would make the sweep
#                        delete that notice on its next run, so the navigation
#                        link to the member area would land nowhere.
#
# A second, path-independent guard backs these entries up. Any captured page
# whose bytes carry a personal detail of the crawling account's owner is
# scrubbed at save time and the page removed by the sweep, keyed on values the
# operator supplies at runtime rather than on anything hardcoded into a
# committed file: the address signed in with, plus the older addresses the
# legacy site still holds for that member. That is what makes the guarantee
# hold for a surface nobody thought to list here.
#
# The crawling account's own profile page is a different matter and is NOT
# removed: it carries the account's alias and the same public fields every
# other member profile carries, so excluding it would cost real archive content
# for one address. It DOES render that address, which this list cannot reach and
# the runtime scrub does: the legacy templates print an e-mail split by empty
# inline tags, invisible to a reader and, until the matcher learned to span
# them, invisible to the scrub as well. The profile is served under both the
# numeric member id and the alias, so the same page arrives more than once and
# the scrub, not a path list, is what covers every form of it.
