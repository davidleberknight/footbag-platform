# Footbag Website Modernization Project -- Claude Code Guide

**Document Purpose:**

This document explains how this repository's Claude Code harness works, why it is built that way, and how it meets Anthropic's published best practices. Contributors are expected to understand it before using Claude Code in this repository. It assumes general familiarity with Claude Code: the official Anthropic documentation covers the product, and this document covers this repository's application of it.

This document is not loaded into Claude's context automatically; it carries no `paths:` glob and nothing imports it, so its length costs no agent context. The files it describes are the source of truth: `CLAUDE.md`, `.claude/rules/*`, `.claude/skills/*`, `.claude/hooks/*`, `.claude/agents/*`, and `.claude/settings.json`. Where this document and one of those files disagree, the file wins and this document is stale.

## 1. Design Premises

The harness follows from three premises. Every practice below is one of them applied to a concrete part of the system, and each section closes with the Anthropic guidance it follows, noting where the repository deliberately goes further.

1. **Context is finite, and every loaded token competes.** An agent reasons better over a small, relevant working set. The harness loads the minimum at session start and reveals the rest on demand.
2. **An instruction is a request; only machinery guarantees.** An agent follows prose probabilistically. Anything that must always hold is enforced by a deterministic hook or a permission rule, never by prose alone.
3. **The harness is production configuration.** It is version-controlled, reviewed, and tested like application code, because a defective line in it misdirects every future session.

The root `CLAUDE.md` is the natural next read after this document.

## 2. Progressive Disclosure

The first premise in practice: the always-loaded layer is a table of contents, and the chapters open only when a task needs them.

**What loads when:**

- *Always, every session:* the root `CLAUDE.md` (kept deliberately short), the one rule that carries no `paths:` glob (`asking.md`), the top of the `MEMORY.md` index (roughly its first 200 lines / 25 KB), and the one-line `description` of every skill Claude may invoke. Metadata only, not the skill body; a skill marked `disable-model-invocation: true` has no description in context at all.
- *Lazily:* a nested `CLAUDE.md` loads when a file in its subtree is opened; a rule with a `paths:` glob attaches when a matching file is Read, Written or Edited, or viewed whole by a Bash command that counts as a read (`cat` or `head` on a single file), never on a grep or reasoning about an unopened path.
- *On demand:* canonical documents under `docs/`, a skill's full body (loaded when invoked, then resident for the session), and individual memory entries.

**In this repository:** detail lives where it loads only when relevant. A convention for editing controllers is a `paths:`-scoped rule, not a line in the root `CLAUDE.md`. A skill's long reference material moves into sidecar reference files beside it so the `SKILL.md` body stays under the roughly 500-line ceiling; `bug-hunt` (with `REFERENCE.md` and `DESIGN.md`) is split this way, and its body dispatches those sidecars to read-only subagents rather than reading them itself, so the heavy catalogs load only in a subagent's context.

**Official grounding:** Anthropic's progressive-disclosure model, the instruction to keep `CLAUDE.md` concise ("Would removing this cause Claude to make mistakes?" If not, cut it) with a target of under 200 lines per file, the roughly 500-line `SKILL.md` ceiling, and the documented rule that a rule file without a `paths:` glob loads at launch exactly like `CLAUDE.md`, so moving text into an unscoped rule saves no context.

## 3. Path-Scoped Rules: Where Coding Conventions Live

Rules are the workhorse of the harness: nearly every line of code Claude writes here is governed by one. `.claude/rules/` holds a convention file per application layer: controllers, services, views, the database layer, database write safety, adapters, tests, code comments, secret handling in scripts, operator scripts, and the Terraform trees — plus `private-repo.md` for the authorized-only private operations checkout, `doc-governance.md` for the documentation, and `claude-harness-governance.md` for the harness itself. The production service units are deliberately outside that set: they are short, they are reinstalled from the release tree by every deploy, and their contract is stated in the design decisions and the private operations reference rather than in a path-scoped rule. Each of these fourteen carries a `paths:` glob, so it attaches exactly when a file in its layer is opened and costs no context before that; the one exception is below.

This is what keeps the root `CLAUDE.md` small without losing precision: the always-loaded file states process and non-negotiables, and the per-layer detail lives in the rule that loads only when that kind of code is being touched. When needed, the convention arrives verbatim, not paraphrased from the agent's memory of a long system prompt.

Two design details:

- **Attachment has a known gap, and the harness compensates.** A rule attaches on Read, Write or Edit of a matching file, or a single-file `cat` or `head`, never on a grep. The root `CLAUDE.md` therefore imposes a pre-writing-code gate: before writing, the agent must enumerate the paths the change will touch and Read each path's governing rule itself rather than trusting auto-attach.
- **One rule is deliberately glob-less** because it is not tied to one subtree; it is linked by name from `CLAUDE.md` and the skills that need it: `asking.md` (putting a question to a human, including approving documentation edits by batch or scoped pre-approval). The memory write gate is a hook, `guard-memory-write.sh`, because it governs one rare action outside the repository and costs nothing until that action happens. What design intent is, when it is clear, and how a disagreement between code, a document and the intent is resolved (from the intent down, settled and reported when clear, a question for the human only when not) is the `design-intent` skill: it loads only when needed, and the pre-design gate in root `CLAUDE.md` loads it in plan mode and whenever deciding what to build, while the root authority order keeps the resolution rule in every session. The deployed-surface method is likewise not a rule: it is its own skill, `.claude/skills/deployed-surface/SKILL.md`, marked `user-invocable: false` and cited by path from the four skills that use it, so it loads when one of them runs instead of in every session.

**Official grounding:** Anthropic's guidance to keep `CLAUDE.md` minimal and move detail into scoped, on-demand files, and the 5-series prompting guidance that instruction files written for earlier models are often too prescriptive, since one brief instruction now steers what an enumeration used to. The pre-writing-code gate goes further, closing an attachment gap the vendor documentation does not call out.

## 4. Layer Activation and Subagent Behavior

The harness is designed around the precise trigger for each layer, and around how the picture changes inside a subagent.

**In the main session:**

- The **root `CLAUDE.md`** loads at session start and stays in context.
- A **nested `CLAUDE.md`** loads when a file in its subtree is opened.
- A **path-scoped rule** attaches when a matching file is Read or Edited (Path-Scoped Rules above covers the gap this leaves).
- A **skill's** one-line description is always in context; the body loads when a task matches it or the skill is named. A skill marked `disable-model-invocation: true` never auto-fires: it runs only when named, and its description leaves always-loaded context.
- A **hook** fires on the tool call its matcher names, before the tool runs (PreToolUse: allow, ask, or deny) or when the agent attempts to stop (Stop). The Bash matcher wires several guard hooks and a read-only auto-approver; when decisions differ, deny and ask always beat allow, so the guards win regardless of execution order.
- **Memory:** the index is always loaded; an individual entry is pulled on recall.

**Inside a subagent** (`auditor`, `researcher`, or any Task-spawned agent):

- A subagent runs in a fresh context with its own system prompt from its `.claude/agents/*.md` definition and its own tool allowlist. It does not inherit the parent's conversation or Plan Mode state. General-purpose and custom subagents load the `CLAUDE.md` files and the unscoped rules at start; `Explore` and `Plan` do not, and every subagent picks up a nested `CLAUDE.md` or a path-scoped rule when it works with matching files. Memory never reaches a subagent. Both custom agents pin `model: sonnet` in their frontmatter.
- **Permission rules** (`settings.json` `permissions.*`) do apply to its tool calls. This inheritance is the guaranteed, version-proof floor a subagent can always count on.
- **`settings.json` hooks fire for a subagent's tool calls, and frontmatter hooks add to them.** Claude Code runs the project's PreToolUse Bash chain — the guards and the read-only auto-approver — inside subagents, and a PreToolUse hook declared in an agent's own `.claude/agents/*.md` frontmatter fires for that agent's calls too, alongside the inherited permission rules. The `auditor` (which has `Bash`) still declares the full Bash guard chain and the read-only auto-approver in its frontmatter, so it stays protected even on a client version that does not fire settings hooks in subagents. The `researcher` declares none by design — it has no `Bash`, `Edit`, or `Write`, so there is nothing to guard.
- **Two layers, not one, and deliberately so.** The frontmatter hooks and the permission floor are defense-in-depth for each other: the permission rules carry every statically-expressible guard as the version-proof guarantee. A subagent spawned as a *built-in* type through the Agent tool (`Explore`, `general-purpose`, `Plan`) carries no custom frontmatter, but current Claude Code fires the settings-wired hooks inside it, so it gets the read-only auto-approver and the guard chain on top of the permission floor and its own tool restriction — read-only research runs prompt-free there without routing it through a custom agent.
- Because the approver may run inside a subagent where, on some client versions, a sibling guard does not fire, it is written to be **self-sufficient**: it never grants a command head while a write- or exec-capable predicate is present (`find … -exec`, even quote-obfuscated; `sort -o` and `sort --compress-program` (the latter runs an external program on sort's temp-file spill); `date -s`; a `sed` write/exec command; a `sqlite3` shell/file dot-command; a mutating `git reflog expire`/`delete` subverb), rather than leaning on a neighbour hook to catch what it waved through.
- A subagent cannot ask the human. It returns question candidates in its report for the main agent to raise under `.claude/rules/asking.md`.

**Authoring consequence:** every guard a static permission rule can express still goes in `settings.json`, because that is the one layer a subagent always inherits. The read-only auto-approver and the positional guards (a mutating flag later in the argument list) are additionally wired into the frontmatter of any custom agent that has `Bash`, so that agent is protected too — and the parser is kept conservative enough to be safe as a lone approver.

**Official grounding:** the documented subagent permission-inheritance behavior (a built-in subagent inherits the parent's permissions), the documented firing of settings hooks inside subagents (the hook input carries `agent_id`/`agent_type`), and the agent-frontmatter `hooks:` schema that runs alongside the project hooks. The design keeps the permission floor as the version-proof guarantee and the hooks as defense-in-depth.

## 5. Document Routing

Routing is how the agent gets from the always-loaded entry point to the exact document a task needs.

**The chain:** root `CLAUDE.md`, then `PROJECT_SUMMARY_CONCISE.md` (an orientation index whose routing table names the document for each kind of need), then the canonical design documents (`docs/USER_STORIES.md`, `docs/DESIGN_DECISIONS.md`, `docs/DATA_MODEL.md`, `docs/DATA_GOVERNANCE.md`, `docs/TESTING.md`) and the maintainers' private tracker (read on demand via `gh issue list -R "$FOOTBAG_PRIVATE_REPO"`; the `tracker-ops` skill owns the workflow, and a machine without the wiring simply skips the read, because the private repo is optional for a developer or tester — though not for an operator, whose Terraform values and runbooks live only there).

**Routing is not optional, and one gate makes it binding.** Progressive disclosure means the design documents are loaded on demand, which leaves a gap the rule-attachment gap does not cover: an agent reasoning about an architecture may never open the document that already rules on it, because nothing it is doing touches a governed path. The root `CLAUDE.md` therefore imposes a *pre-design gate* beside the pre-writing-code gate. In plan mode, and before proposing an approach or explaining why something is built as it is, read the governing passage: the user stories' success criteria for functional requirements, the design decisions for technical and non-functional ones; then say which passage governs or that none does. It exists because an agent reasoning from the code and the conversation will otherwise defend a design the governing passage already rejected. The gate is prose, so it is a request rather than a guarantee. No hook can observe that a document was consulted before a claim was made, and the Stop hook that could inspect the finished message has no trigger as cheap and exact as the question mark the question-quality guard keys on. Machinery would be the stronger answer if a precise trigger is ever found.

**The load-bearing distinction:** canonical documents carry timeless design intent and the private tracker carries implementation status; `.claude/rules/doc-governance.md` holds the rules that keep them apart, including deleting a reversed ruling rather than marking it superseded. Keeping status in the tracker also keeps it out of always-loaded context.

## 6. The Three Orders

Three orderings are easy to conflate, so each has exactly one home and is linked to by name; a duplicated instruction drifts, and a drifted copy is worse than none.

- **Authority order:** which source wins when sources conflict. Single home: the root `CLAUDE.md`.
- **Read order:** what to load first to conserve context. Also in the root `CLAUDE.md`, and explicitly not an authority ranking.
- **Composition order:** when several skills apply to one task, the sequence to run them in. Stated once in the root `CLAUDE.md`.

This document intentionally does not reproduce the rankings; they live in `CLAUDE.md`, for the same single-home reason.

## 7. Deterministic Guardrails

The second premise in practice: enforcement that does not depend on the agent choosing to comply.

**Deny beats ask when a rewrite exists.** A guard has three outcomes, and choosing between them is a policy, not a per-hook quirk. *Allow* when the command is provably inert. *Ask* when it genuinely writes or reaches something, because that is the human's decision. *Deny* when the command is not statically analysable but an equivalent analysable form exists — a leading `cd`, a shell loop, process substitution, a redirect target written as a variable, a redirect into the working tree (rewritten as an Edit or Write). A denial there costs only a rewrite, while an ask costs a human interruption on work that was never theirs to adjudicate. This is what keeps read-only research from ever reaching a prompt: it either proves itself inert, or it is sent back to be written so it can. Never add an ask for a command the agent could simply express differently.

**What is enforced.** Two hooks run on Edit and Write: `block-secrets.sh` blocks changes to secret-bearing files, judging a `.env` file by its name at any depth or in a companion checkout, and `guard-memory-write.sh` denies a write to the memory store until the write carries the pre-save audit line in the memory file's frontmatter, its deny reason stating what memory may hold. A chain of hooks runs on every Bash command:

- (`block-git-mutations.sh`) hard-denies every write to the repository and to its GitHub remote. It parses each command the way a shell would rather than matching a list of verb spellings: split at shell separators where the shell would (a separator inside quotes is text, while a `$(…)` or backtick opens a command even inside double quotes), strip environment assignments and wrappers (`env`, `command`, `sudo`, `xargs`, and a `bash -c` or `eval` whose string argument is split and judged in turn), resolve the binary (`git` or `gh`, absolute path included), skip git's own global options so a leading `-C DIR` or `-c k=v` cannot hide the verb behind it, then judge the verb actually being run. A spelling list blocks only the verbs someone thought to list, so this gate never regresses to one. Verbs with no read-only form are denied outright; the dual-mode verbs (`branch`, `tag`, `remote`, `worktree`, `stash`, `submodule`, `notes`, `reflog`, `config`) are denied unless what follows is one of their listing forms, so `git branch -vv` and `git tag -l` still read while `git branch feature` does not. The same rule holds on the GitHub CLI — pull requests, releases, workflow runs, keys, repository settings, and any `gh api` call that is not a GET, except a GraphQL read: a `gh api graphql` call is refused only when the command carries a mutation or a subscription anywhere, or a body the gate cannot see — with issue operations as the one sanctioned exception, since working the maintainers' private tracker and the private bug-intake repository is the workflow the permission rules already grant. A `gh api` write to an issue endpoint is still refused, because those rules match only the `gh issue` repo-flag form, and the refusal names that rewrite; the one exception is editing a single comment on the private tracker with its body from a file (`gh api -X PATCH repos/<tracker>/issues/comments/<id> -F body=@<file>`), the one issue write that form cannot express, which the settings deny list leaves open only in that spaced `-X PATCH` spelling. A verb the parser cannot resolve because it sits behind a variable or a command substitution is denied rather than guessed: an invocation the gate cannot read is the case it exists for;
- (`guard-secret-reads.sh`) blocks reads of secret-bearing files;
- (`guard-prod-ops.sh`) asks before three production-shaped mutations, each matched at command position: a `terraform` apply, destroy, import, `state rm`, taint or untaint when the command also names production; a `systemctl` start, stop, restart, reload, enable, disable, mask, unmask or daemon-reload in any environment; and a `docker compose` up, down, restart, stop, rm, pull or build when the command names `/srv/footbag`, production or a compose file;
- (`guard-aws-reach.sh`) asks before anything that reaches AWS, every invocation: the `aws` CLI, and the Terraform subcommands that contact the account or the remote S3 state (`init`, `plan`, `apply`, `output`, `refresh`, `state`, and the rest; this hook ignores the local `fmt` and `validate`, though the `Bash(terraform:*)` ask rule still prompts for every terraform command). Crucially it also reads the scripts a command names — literal `.sh` paths and whatever an `npm run <name>` resolves to, followed one level deeper — because a permission rule matches the command prefix and a wrapper script's name reveals nothing about the AWS calls inside it. Matching is anchored to command position with optional leading `VAR=value` assignments and the words that run the command after them (`env` with its options, `sudo`, `command`, `exec`, `nohup`, `time`, `xargs`), so `env -i aws ...` asks while `aws` as a bare argument (`grep -rn aws src/`) does not prompt and the guard stays signal rather than noise. A script path counts as run only where the shell would run it: as the command, or as an interpreter's script operand; a path inside another command's quoted argument is data. Script bodies are read the same way: comments and the contents of quoted strings are data, so a regex, a test fixture or a printed message naming the aws CLI never prompts. Wherever a string can become code (an `eval`, an interpreter's `-c`, `ssh`, `sudo`, a heredoc fed to a shell, an inline program such as `python -c` or awk's `system()`, a pipe into a shell, sourcing stdin or a process substitution, a variable run as a command, or an argument forwarded to any of these), the guard falls back to reading the raw text; the only strings it no longer reads are ones run by a route outside that list, and each route the repository's scripts use is in it and in the fixture suite. Even in that raw reading, a line that only prints (an `echo` or `printf` with no command substitution, backtick or pipe) and a heredoc no shell reads stay data, so a hint naming another script is never taken for a run. A script that runs a command from a variable takes its program from that variable, so there a value such as `TF_BIN="${X:-terraform}"`, `AWS_BIN=aws` or `cmd=(aws s3 ls)` counts as the call. A library sourced through a directory variable (`source "${SCRIPT_DIR}/lib/x.sh"`) is followed relative to the sourcing script's own directory, because that library is where such a script's AWS calls live. A heredoc fed to another language, such as a Python program, is that program's text: it is still read for an aws call, but a script path inside it is not taken for a shell run. A script whose first command is `aws_isolate_self "$@"` (from `scripts/lib/aws-isolation.sh`) re-runs itself with every AWS credential source broken, so the guard trusts it without reading its body; the hook fixture suite and the harness self-check do this, because their fixtures name the aws CLI as data. A script that later exports, unsets or reassigns an `AWS_` variable, or runs `env -i` / `env -u`, is read as usual. The decision is always `ask`, never a cached allow, so approval is per-invocation and Claude reaches AWS only on an explicit human yes;
- (`guard-db-destructive.sh`) asks before five database actions, each matched where the command actually runs it: running `scripts/reset-local-db.sh`; an `rm` of `footbag.db` or its `-wal`/`-shm` files; `sqlite3` given inline destructive SQL (DROP TABLE or INDEX, DELETE FROM, TRUNCATE, ALTER … DROP); destructive SQL piped or redirected into `sqlite3`; and any writable `sqlite3` use (INSERT, UPDATE, REPLACE, CREATE, ALTER, ATTACH, VACUUM INTO, or the `.read`, `.import`, `.restore`, `.output`, `.save`, `.backup`, `.clone` or `.dump` dot-commands);
- (`guard-dangerous-git.sh`) guards any git command carrying a command-running or file-writing flag (`--upload-pack`, `--receive-pack`, `--exec-path`, `--open-files-in-pager` run a command; `--output` writes a file), so a statically-allowed `git fetch` cannot shell-exec via `--upload-pack` unprompted. It also names the work-discarding verbs (`reset --hard`, `clean -f`, `checkout --`, `restore`, `branch -D`), which the git-mutation block above denies outright, so those never reach a prompt; the ask stays as the layer that would still hold if that block were ever narrowed;
- (`guard-find-exec.sh`) hard-denies (deny-beats-ask, above) `find` command-execution predicates (`-exec`, `-execdir`, `-ok`, `-okdir`), including quote- and backslash-obfuscated spellings such as `find . '-exec' …`;
- (`guard-leading-cd.sh`) hard-denies (deny-beats-ask, above) a command that begins with `cd` or `pushd` (including just inside an opening subshell paren), so a leading directory change is rewritten away instead of tripping the built-in `cd`-plus-redirect prompt;
- (`guard-shell-loop.sh`) hard-denies (deny-beats-ask, above) a command carrying a shell loop (`while`/`for`/`until` … `do`) at command position, so a hand-rolled loop is rewritten as simple statically-analyzable commands or the Grep/Read tools instead of tripping the built-in prompt for a command it cannot statically analyze; a loop keyword that is only an argument, inside quotes, or unaccompanied by a `do` (`grep -w for`, `echo "a; while b"`) is not matched, and a loop inside a committed script is invisible here because the command names the script, not the loop;
- (`guard-interpreter-writes.sh`) hard-denies (deny-beats-ask, above) a command that hands an interpreter an inline program which writes a file: a heredoc, or a `-c` / `-e` / `--eval` program, calling `open(…, 'w')`, `writeFileSync`, `write_text`, `File.write`, `shutil.move`, Perl's `open` with a `>` mode, or a similar write. The rule it enforces is that files are edited through the Edit and Write tools, where a change gets a diff preview and review, and an interpreter fed its program inline writes without any shell redirect for the redirect guard to see. All three conditions must hold, so a read-only inline program (parsing JSON, computing line numbers) is untouched, and a committed script under `scripts/` is invisible here because the command names the script rather than the program. The interpreter name is matched with an optional version suffix and the flag with or without a following space, because `python3.11` and `node -erequire(…)` are the same construct as their tidier spellings and a guard that misses them is a guard in name only;
- (`guard-process-substitution.sh`) hard-denies (deny-beats-ask, above) a command carrying process substitution (`<(…)` or `>(…)`), so a comparison written as `diff <(…) <(…)` is rewritten as the Read tool or as two plain commands writing to stdout, instead of tripping the built-in prompt for a command the analyzer cannot statically decompose; the match is the bare two-character sequence, so a quoted occurrence is denied too, because a guard that parsed shell quoting to tell those apart is how guards acquire bypasses and a false deny costs only a rewrite;
- (`guard-readonly-bash.sh`) asks about mutating flags that ride on otherwise read-only commands (`find -delete`/`-fprint`/`-fprintf`/`-fls`, `sort -o`, `sort --compress-program`, `tree -o`, `sed -i` and `sed`'s `w`/`e` write/exec commands, and `curl`'s mutating methods `-X POST/PUT/DELETE/PATCH`, upload/data flags, and `-o`/`--output` to a real file);
- (`guard-readonly-bash.sh`) hard-denies an unambiguous output redirection into the working tree (a relative target, or an absolute one under the project directory), because files here are edited through the Edit and Write tools where the change is shown as a diff, and an ask can be approved without the write being read; it asks on any other output redirection to a real file (`> file`, `>> file`), whatever read-only-looking head precedes it, because a static allow for that head (`cat`, `egrep`, `date`, a read-only `git` subcommand) would otherwise auto-approve the write; the check is deliberately head-agnostic (it strips the exempt targets and asks if any redirect remains) so it cannot drift out of sync with the allow list, and spacing is irrelevant (`>out` gates exactly as `> out`). The discard device (`/dev/null`) and the session scratchpad directory (`/tmp/claude-*/…/scratchpad/`) are exempt; a bare `/tmp/claude-*` path outside the scratchpad still gates. A target written as a shell variable is hard-denied rather than asked (deny-beats-ask, above): the guard cannot prove where `"$VAR/file"` lands, and an unprovable destination is a command to rewrite, not a decision to put to the human. Spelled literally it gates on its own merits;
- (`guard-rm.sh`) auto-approves an `rm` that deletes only files under the session scratchpad directory, and asks for every other `rm` (so scratchpad cleanup does not prompt while real deletions still gate);
- (`guard-full-suite-vitest.sh`) asks to confirm a direct `vitest run` that names nothing narrower than a whole tier, because that is the full gate the maintainer starts, and a whole-tree run also bypasses the excludes baked into `npm test` and collects the Playwright specs under `tests/e2e`, which cannot run under vitest; each `vitest run` in a compound command is judged on its own targets; a run naming a file or folder below a tier defers, while an untargeted run with or without excludes, a bare `tests/` target, a whole `tests/unit` or `tests/integration` tier (including a glob or `.` standing for one), or a test-name filter (`-t` or `--testNamePattern`, whose value is never read as a target) with no path still asks;
- (`guard-foreground-tests.sh`) denies a test runner (pytest, `python -m pytest`, vitest, `playwright test`, `npm test` or an npm `test:*` script, `run_all_tests.sh`) whose Bash call does not set `run_in_background`, because a test run in the foreground blocks every other piece of work until it ends; it judges each subcommand at its command head (after env, `timeout` and similar wrappers, and inside `bash -c`), so a command that merely names a runner is untouched, and a help, version or listing form passes; it fails open on a parse issue;
- (`guard-maintainer-gate.sh`) denies a maintainer-gated command (the full gate, the whole-tier test commands including the whole browser tier, and the deployed, pentest, persona-crawl and smoke test commands, the `run_dev.sh` rebuild modes, and deploy) the first time in a session, telling Claude to say in its message the exact command and why, write the Bash description as that why, and reissue it; the reissue falls through to the `permissions.ask` entry, which prompts as before. A gated command combined with any other command (`&&`, `;`, `|`) is always denied, so the prompt, and any rule it offers to save, names that command and not trailing plumbing; a redirect into the scratchpad is allowed. Its list is copied from the ask list, and the harness self-check fails if an entry is missing there;
- (`allow-readonly-bash.sh`) auto-approves genuinely read-only Bash, with deny and ask decisions from the guards always beating this allow — and the approver itself refusing any write- or exec-capable form rather than relying on a neighbour guard to catch it.

A Stop hook (`guard-question-quality.sh`) blocks low-quality questions to the human, and a question whose message has no `Settled from the sources:` line. A second Stop hook (`require-doc-sync.sh`) keeps a turn from ending while project files have changed since the `doc-sync` skill last ran in the session; a PostToolUse hook (`track-doc-sync.sh`) arms it on any edit inside the project outside `docs/` and clears it when `doc-sync` runs, and plan mode never blocks. A SessionStart hook (`strip-local-allows.sh`), on a fresh session (startup or `/clear`), removes every allow and ask rule a "don't ask again" click saved into `.claude/settings.local.json`, keeping `env` and `deny`, and tells Claude what it removed: Claude Code saves such a click permanently, so this hook is what limits it to one session.

**The ask/deny guards match execution, not mention.** Each guard that gates a specific command or path — the database guard, the git-mutation block, the dangerous-git verbs, the production-ops mutations — anchors its match to command position: the start of the command or a pipeline or list segment, optionally behind a `bash`/`env`/`VAR=` prefix, never a bare inter-argument space. A read-only command that only names the token as an argument — `git log -- scripts/reset-local-db.sh`, a `cat` or `grep` of that file, an `echo` mentioning `git reset --hard` — is not an invocation and does not prompt, while actually running it still asks. This matters because a guard's `ask` outranks the read-only approver's `allow`: without command-position anchoring, every read of a guarded name would override the approver and become a spurious prompt. The fixtures in `scripts/ci/test_hooks.sh` pin both directions — the execution asks, the mention defers — for each guard. The secret-path guard is the deliberate exception: it matches a secret-bearing path anywhere in the command, because naming the file is already the risk.

**Where the whole setup lives.** The guard scripts are in `.claude/hooks/` and are wired with their matchers in the `hooks` block of `.claude/settings.json` (all hooks matching a call run in parallel, and the most restrictive decision wins); the always-on permission floor is the `permissions` block of the same file; the read-only auto-approver is `.claude/hooks/allow-readonly-bash.sh`; and the guard hooks have fixtures in `scripts/ci/test_hooks.sh`. Read those files to see the entire enforcement surface — this document explains the design, not every line.

Read-only is not the same as safe: an allowed read of a secret file plus an allowed network fetch is an exfiltration chain. That is why secret-bearing paths are denied to Bash outright (`guard-secret-reads.sh`), since the Read-tool deny rules do not bind shell commands, and why WebFetch is domain-scoped rather than open.

**Fail mode is chosen per hook:** security gates fail closed and deny on doubt. The read-only auto-approver only ever grants: it emits allow for a command it can prove read-only and otherwise stays silent so the normal prompt decides. How it earns that proof:

- **Segment and vet every head.** It splits the command into segments and checks each head against a read-only allowlist, stripping control keywords, grouping, and negation so a command hidden behind them (`( rm x )`, `! rm x`) is still checked, and stripping read-only wrappers (`timeout`, `nice`, `command -v`) so the wrapped command is what gets vetted. Command-runner heads that execute their argument (`env`, `command CMD`) are not treated as read-only, and a head is rejected when an exec or write flag rides mid-arguments where a prefix rule cannot see it (`git --output`, `git ls-remote --upload-pack`, `rg --pre`, `sed -i`, a second file operand).
- **Refuse a read-only-looking head that can still act.** `find` carrying any action predicate (`-exec`/`-delete`/`-fprint`, matched after stripping quotes and backslashes so `find . '-exec' …` cannot slip through); `sort -o`, and `sort --compress-program`, which runs an external program on sort's temp-file spill; `date -s`; `hostname <name>`; a mutating `git reflog` subverb (`expire`/`delete`, gated because `reflog`'s read-only `show`/`list` forms keep it on the read-only git list); `git fsck --lost-found` (the one `fsck` form that writes, into `.git/lost-found`, gated so plain read-only `fsck` stays approvable); a `sed` that writes or executes. It drops `printenv`, which would dump the whole environment, and it defers on bash 5.2 function substitution (`${ cmd; }`).
- **Admit a few richer tools only in provably inert forms.** Read-only `git` and `gh` by an allow-list of read-only subcommands, accepting `git -C` only for a literal in-project target — a relative path (the working directory is the repo root) or an absolute path at or under the project directory, the gitignored companion-checkout symlinks included by their bare in-project name (the form the root `CLAUDE.md` prefers over a leading `cd`; a `..`/`~` path, or an out-of-tree real path cannot be proven in-project, so the approver stays silent and the command prompts). `sqlite3` only as an inline query on a read-only open (the `-readonly` flag, or a `file:...?mode=ro` URI that names no writable or alternate mode) with no shell-exec or file-write dot-command, no `ATTACH`, no write statement, and no value-setting `PRAGMA` — each refused by the approver itself rather than trusting the engine or a sibling guard. `curl` only as a loopback health probe that discards its body (`-o /dev/null`, with no mutating method, upload, file write, or off-box redirect via `-x`/`--resolve`/`-L`). `unzip` only in a read-only mode (`-p` stream to stdout, `-l`/`-v` list, `-t` test, `-Z` zipinfo) with no `-d` extract target. A redirect to `/dev/null` or the session scratchpad directory (`/tmp/claude-*/…/scratchpad/`, the same area `guard-rm.sh` allows deletes in) is treated as writing nothing.
- **Resolve substitutions fail-closed.** A command substitution is resolved with a quote-aware, paren-balanced scan (so a quoted `count(*)` never moves the boundary), innermost first, accepted only when its inner is a simple read-only command or a read-only `sqlite3` query and passes the same per-head write/exec-flag vetting used at top level — one shared check, so `$(sed -i …)` or `$(git ls-remote --upload-pack=…)` is refused exactly as its top-level form is, rather than head-vetted only. The approver can also resolve an input process substitution `<(...)`, but `guard-process-substitution.sh` denies every one first, so that path never decides. An output `>(...)` writes and is never accepted. A nested read-only substitution resolves one layer per pass. The approver stays silent on a non-read-only inner, arithmetic, a subshell, backticks, a write redirect, or an unquoted separator (a newline included) inside the inner, and it fails closed on any ANSI-C `$'…'` quoting whose escape rules would desync the quote scan.
- **Track quoting exactly.** When it neutralizes separators inside quotes it honors backslash escaping, so a backslash-escaped quote cannot smuggle a live command past the segment split, while a backslash-escaped separator (literal text to bash wherever it sits) is neutralized rather than splitting a phantom segment. Quoted strings are tracked across newlines — an inline SQL query or a `node -e` script spanning lines is one argument, not several commands — and both this approver and the redirect guard read a literal `>` inside quoted argument text (an SQL `<>` comparison, a JavaScript arrow function) as text, not as a write redirect.
- **Stay safe alone.** Because deny and ask always beat allow, a write that slips past it is still caught by its guard — and because the approver also runs inside subagents (where, on some client versions, a sibling guard may not fire), it is kept conservative enough to be safe as a lone approver.

**Static guards are mirrored into permissions.** Anything a static permission rule can express is put in `settings.json`; hooks cover only the positional cases a rule cannot express, such as a `find -delete` or a `curl -X POST` flag anywhere in the arguments (see Layer Activation and Subagent Behavior for why this split protects subagents).

**Official grounding:** Anthropic's guidance that guardrails belong in hooks because an instruction is a request, not a guarantee.

## 8. Permission Policy and Approval Fatigue

The allow/ask/deny policy in `settings.json` embodies a discipline: cut needless prompts without cutting safety. Excess prompting trains a reviewer to approve blindly, which is its own risk.

**What the policy does:**

- **Read-only commands are allowed generally.** Reading files, history, the database (read-only open), the tracker and the network (a GET) never needs the human's approval: the read-only approver grants them, the guards exist only to stop writes, and the asking rule tells Claude to run a read rather than ask about it. Screenshots and other heavy browser-tool reads are the exception and run only when the human asks.
- Precedence is `deny > ask > allow`.
- Wildcard allows are limited to read-only command heads (the first word of a command) plus a short list of deliberate development conveniences: `mkdir`, `kill` and `pkill` for dev-server lifecycle, `git fetch`, `npm run build`, the test type-check `npm run typecheck:tests` (one exact spelling), the narrow local test tier `npm run test:strong-hash`, the whole-site layout check `npm run test:rendered-style` (which the targeted-set helper prints as a check for layout-helper changes), the targeted-set helper `scripts/test-targets.sh`, a browser end-to-end run naming its spec files (`npm run test:e2e -- tests/e2e/<name>.spec.ts`, the form that helper prints), the two direct tool invocations behind those same tiers (`npx tsc -p tsconfig.json --noEmit` as one exact spelling, and `npx vitest run ...` in its run form only, so watch-mode `npx vitest` still prompts and a full-suite run still meets the full-suite guard), and a short reviewed list of repo scripts (the harness self-check, the conventions check, the hook-fixture suite, the generated-content check, the CI-parity check, and the e2e port-reclaim helper). Tracker reads go through the read-only `gh` forms, which the approver grants on their own merits. The heavier tiers are deliberately not auto-approved and so prompt: the live-AWS `npm run test:smoke`, the browser end-to-end tier run whole (`npm run test:e2e` with no spec file, or naming all of `tests/e2e`), the heavy pentest tier, the everything-run `npm run test:all` (local only, but it starts the e2e stack), the runner itself in every mode, and every whole-suite or whole-tier vitest command (`npm test`, `npm run test:quick`, `test:unit`, `test:integration`, `test:coverage`, and the exact `npx vitest run` spellings with no target, a bare `tests/`, or a whole `tests/unit` or `tests/integration` tier). Those sit in `ask`, which prompts even in auto mode and inside subagents: the full gate is the maintainer's decision, and Claude verifies each change with the targeted set the helper prints (the Verification default in root `CLAUDE.md`). Destructive, history-rewriting, package-installing, and service-touching commands sit in ask or deny, including the four dev-stack rebuild modes that wipe the local database (`run_dev.sh` with `--reset`, `--from-csv`, `--all-data` or `--soup-to-nuts`).
- The remaining test tiers in `ask` are there for their cost and reach, not because they write: the deployed-site check (`npm run test:deployed*`) drives a live staging or production site from outside; and the persona crawl (`npm run test:persona-crawl*`) is a heavy whole-site crawl. Before running any gated command Claude says what it runs and why (the maintainer gate above enforces this for these tiers).
- Claude Code checks each part of a compound command (`&&`, `;`, `|`) against the rules independently. A rule matches the command text Claude writes, so it catches only the spelling it names: a mutating flag in another position or spelling (`curl -X POST`, `--request POST`) and the same program called another way (`/usr/bin/curl`, `sh -c '...'`) slip past it; those cases are what the guard hooks cover.
- Network reads route through domain-scoped `WebFetch(domain:...)` allows and WebSearch rather than an allowed `curl`. The one auto-approved `curl` is a loopback health probe that discards its body (`curl -o /dev/null http://localhost/…`); every content-returning or off-box `curl` prompts, because content is fetched through WebFetch, not an auto-approved `curl`. `sqlite3` is auto-approved only for an inline read-only query on a read-only open (`-readonly`, or the `file:...?mode=ro` URI), through the approver hook; and read-only `gh` subcommands auto-approve on their own merits. Four `gh` write forms also auto-approve, and only these: editing, commenting on, closing, and reopening an issue, each allowed by an exact prefix that includes a repo flag naming the private tracker or the private bug-intake repository, so a rule matches only when the command is written `gh issue edit -R "$FOOTBAG_PRIVATE_REPO" …` or `gh issue edit -R "$FOOTBAG_DEVTESTER_REPO" …` and never covers another repository. That is a deliberate trade: an issue edit is reviewable and reversible, the human's decision to change a card is already the sign-off (the `tracker-ops` skill's one-ask-per-batch rule). Filing a new card still prompts, because scope creep is the risk there; deleting an issue or a repository is denied outright; every other `gh` write form is denied, `gh issue develop` included.
- Lightweight Playwright browser-driving auto-approves so routine UI testing does not prompt: navigating, reading the accessibility snapshot, clicking, hovering, typing, filling forms, selecting options, pressing keys, waiting, reading console output, resizing, tab control, and closing. Screenshot capture (`browser_take_screenshot`) is the heavy mode (large token cost) and stays in `ask`, and network-request dumps (`browser_network_requests`) are heavy too and sit in `ask` beside it; browser JavaScript execution (`browser_evaluate`, `browser_run_code_unsafe`) and the other browser side-effect tools are never allowed and prompt by default.
- Prompts are reduced in only three safe ways: the auto-approver hooks (`allow-readonly-bash.sh` for read-only commands, and `guard-rm.sh` for an `rm` confined to the scratchpad directory), narrowly scoped exact allows, and per-developer OS sandboxing that is never committed. The built-in `fewer-permission-prompts` skill proposes read-only allows for the committed `settings.json` from transcript history; each proposal is reviewed as a harness change.

**The approval-fatigue fix, concretely.** A permission allow rule is a prefix match on a string; it cannot parse a compound command or see a mutating flag later in the arguments, so it can never safely auto-approve the kind of command real research uses — a pipeline, a `$(…)`, a `VAR=… cmd`. That is the job of `allow-readonly-bash.sh`, a PreToolUse hook that actually parses the Bash command: it splits every segment (across `&&`, `;`, `|`, subshells, control constructs), strips read-only wrappers, vets each command head against a read-only allowlist, resolves `$(…)` fail-closed, and returns *allow* only when the entire command is provably read-only. Anything it cannot prove inert it leaves alone, so the normal prompt decides. The result: complex read-only research runs without a prompt, while a genuinely mutating command still stops — the specific outcome the "read-only never asks, mutations still gate" requirement demands. This is the same class of solution (real shell parsing, not prefix matching) that the tools which credibly reduce this fatigue all converge on.

**One deliberate exclusion, `awk`.** A few commands read in their common form but can write a file through their own syntax, where no flag and no shell redirect reveals it: `awk` writes with an in-program `print > f`, so the approver cannot prove any `awk` invocation inert. Rather than auto-approve a possible write, `awk` is left off the read-only allowlist and prompts. Read-only text processing that would reach for `awk` uses the allowlisted substitutes instead: `cut` for fields, `grep -oE` for pattern extraction, `jq` for JSON, `sort` with `uniq -c` for counting, and `paste` / `column` / `tr` / `sed` (print or substitute to stdout, never `-i`) for reshaping. `printenv` is excluded on a related principle: it would dump the whole environment, including any secret-bearing variable.

One prompt class the harness cannot remove is Claude Code's own built-in check: a compound command that begins with `cd` and also redirects output (even `2>/dev/null`) is flagged as a possible path-resolution bypass. That guard lives inside the product, not in this repo's settings or hooks, and because an `allow` never outranks an `ask`, no hook or permission rule here can suppress it — even though the read-only auto-approver would otherwise allow the command. It is avoided two ways: the root `CLAUDE.md` instructs relying on the persistent working directory and absolute paths (or a tool's own directory flag) rather than prefixing `cd`, and `guard-leading-cd.sh` denies any command that begins with `cd` or `pushd` (including one just inside an opening subshell paren), so the pattern never reaches that built-in check.

The same built-in analyzer raises a second prompt no permission rule here can suppress: a compound command it cannot statically decompose — one carrying a shell loop, a `<(…)` process substitution, a `$(…)` command substitution, or a `$((…))` arithmetic expansion — is flagged "cannot be statically analyzed," because it cannot prove every command that will run is read-only. That verdict is correct; the design question is only where the interruption goes, and this is where the three PreToolUse decisions differ by audience. An `ask` prompts the human; an `allow` runs silently; a `deny` blocks the call and returns its reason **to the agent**, as the result of that tool call, not to the human. `guard-shell-loop.sh` uses that third path: it denies a hand-rolled loop with a reason that reads as an instruction — rewrite this as the Grep/Read tools or simple, statically-analyzable commands. The agent receives that reason exactly like a tool error and reissues the command loop-free, and the human is never asked. It works inside a subagent too, which cannot ask a human at all: the same hook fires there, the deny reason lands in the subagent's own context, and the subagent revises its research command itself. So the guard does not merely relocate a prompt — it converts a human interruption into machine-readable feedback the model acts on.

The response is a deny-and-rewrite guard rather than an auto-approver for safety. Auto-approving compound shell cannot be made safe: a nominally read-only tool can still write through its own mini-language (`sed`'s `w` command, `awk`'s `print > f`), a loop variable routinely feeds exactly that script argument, and a `$(…)` can hide a write — so a hook conservative enough to be safe would only re-implement the analyzer's own refusal. A deny is safe by construction: it can never green-light a hidden write, and the worst case is a false deny that gets reworked. The guard is deliberately narrow — it matches a loop keyword only at command position and only alongside a `do` — and it is modeled on `guard-leading-cd.sh`, which denies a leading `cd` the same way. `guard-process-substitution.sh` takes the same path for `<(…)` and `>(…)`, whose subshells the analyzer cannot decompose either, and whose work is always reachable another way: read the files with the Read tool, or run two plain commands writing to stdout. Command substitution and arithmetic are deliberately left to the built-in prompt, since those are occasionally legitimately needed and denying them outright would over-block.

**Repo-wide vs machine-local: where a rule belongs.** Three files hold permission rules, and which one a rule lives in is a deliberate decision, not an accident of where it was first clicked:

- `.claude/settings.json` — **repo-wide.** Committed and version-controlled, so every developer and CI get the identical policy. All deliberate allow/ask/deny rules and all hook wiring live here. This is the default home for anything shareable and platform-independent. It also registers the private operations checkout as an additional working directory, by both its link name `footbag_private_repo` and the standard sibling path `../footbag-ops`, because an edit through a link is checked against both (Companion Repositories below). Claude Code judges an edit by the real folder a link resolves to, so without the registration every edit to a private ops document prompts separately; with it, drafting there follows the same rules as drafting in this repo. A machine without the checkout has no such folder, and the entry names nothing there.
- `.claude/settings.local.json` — **machine-local, per-developer.** Gitignored, so it is never shared and is absent in CI. It is where clicking "don't ask again" at a prompt silently writes a rule, permanently, so it drifts toward over-permission by construction. Here such a click lasts one session: `strip-local-allows.sh` removes every saved allow and ask rule when a fresh session starts. The file legitimately holds the `env` block carrying machine-local values that committed text must never name, such as the `FOOTBAG_PRIVATE_REPO` slug of the maintainers' private repository (the hidden-reference rule), and any deny rule, which only tightens. A permanent never-ask is written by hand: a shareable, platform-independent rule into the committed `settings.json`, including a reviewed repo-script allow, and a rule naming an absolute machine path into the user-global file below, scoped by that path. The harness self-check fails on any allow or ask rule left in this file, and on a deny rule carrying a destructive command head; the `env` block is never scanned. Claude never writes this file itself: a `permissions.ask` guard on `Edit` of `.claude/settings.local.json` in the committed `settings.json` routes any such edit through the human, and a Claude-initiated `Write` of the file is banned outright by root `CLAUDE.md` regardless of permission rules, because the always-allow click, not Claude, is its only intended writer.
- `~/.claude/settings.json` — **user-global, per-machine, every project.** The home for a machine-specific rule that genuinely applies across every project: the session scratchpad directory (so the AI's own temp/scratch files never prompt; a Bash redirect that writes into that directory is additionally exempted by the read-only approver and the redirect guard, and an `rm` confined to that directory is auto-approved by `guard-rm.sh`) and the memory-store path. These cannot be committed — an absolute home path is wrong for every other machine, and the team-portability rule forbids machine-specific paths in `.claude/`. A machine-specific rule that matters only inside one project belongs in that project's local file above instead, so it is not widened to every repo you open.

Precedence across all three is `deny > ask > allow`: a `deny` at any scope wins, and a local `allow` can only loosen, never override, a committed `deny`. Rule of thumb: **repo-wide for all shared, platform-independent policy; machine-local only for an absolute path unique to one computer.**

**Official grounding:** the permissions documentation's `deny > ask > allow` precedence and per-part compound-command checking, its recommendation to prefer `WebFetch(domain:...)` over `curl`, the settings documentation's scope-merge behavior, and the sandboxing guidance.

## 10. Memory Discipline

Memory is a small, indexed store of durable facts, treated as a scarce resource that competes for context like everything else.

Memory holds only machine-local facts and the user's own working preferences; every project fact goes to a canonical home, because memory is per-machine and never reaches subagents or other developers. The gate is `.claude/hooks/guard-memory-write.sh`, which denies a write to the memory store until the write carries the pre-save audit line in the memory file's frontmatter, its deny reason stating the classes and exclusions; the `audit-memory` skill applies the same checklist to the whole store on request.

**Official grounding:** the memory documentation states that auto memory is machine-local, not shared across machines, and not loaded into subagents. It also lists project context as a use for auto memory; this project deliberately narrows that, since no teammate or subagent would see it.

## 11. Harness Change Control

The third premise in practice: the workflow for editing the harness itself. Its single home is `.claude/rules/claude-harness-governance.md`, which auto-attaches whenever a `.claude/**` file is opened.

In short: Plan Mode and literal before/after approval for any non-trivial change; a permission rule before a hook wherever one can express the guard; a fixture test for every hook; skills with a precise trigger, a stop condition and no `allowed-tools`; and a periodic `/doctor prompt-audit`. The rule has the detail.

**Why this rigor:** a committed `.claude/` directory that any contributor, or a compromised dependency, could alter is a real attack surface. A malicious `.claude/settings.json` can reach code execution and credential exfiltration before a trust prompt appears. Treating the configuration as reviewed, tested production code is the mitigation, and keeping platform-specific settings in each developer's own uncommitted `~/.claude/settings.json` keeps `.claude/` behaving identically for everyone.

**Official grounding:** Anthropic's guidance to version-control and review Claude Code configuration. The fixture-test requirement for hooks goes further.

## 12. Continuous Self-Verification

`scripts/ci/assert_claude_harness.sh` verifies that the harness stays internally consistent. It checks that:

- `settings.json` is valid JSON;
- every wired hook exists and is executable;
- no live file references a deleted document;
- every mention of `DEVOPS_GUIDE.md` names it as private on the same line;
- explicit-only skills carry `disable-model-invocation`;
- every `SKILL.md` is 500 lines or fewer, with no exception;
- `sqlite3` is never auto-allowed without `-readonly`;
- every concrete rule, skill, hook, and agent reference resolves, in every `CLAUDE.md` (root and nested), `PROJECT_SUMMARY_CONCISE.md`, this guide, and every `.md` under `.claude/`;
- every rule's `paths:` glob matches at least one file in the tree, except a glob under a gitignored companion checkout;
- the committed allow list never regains a mutation-capable command head or an unscoped `WebFetch(domain:*)`;
- no harness file depends on a machine-local memory-store path;
- the hook fixture suite passes, so a reopened bypass or a new over-block fails the build;
- the machine-local `settings.local.json`, when present, carries no saved allow or ask rule, and no deny rule with a destructive command head;
- every command the maintainer gate hook gates is also a `permissions.ask` entry, so the ask list stays the floor beneath it;
- every agent-frontmatter hook resolves to an executable file, and an agent that has `Bash` declares exactly the `settings.json` Bash hook chain, so the two layers cannot drift apart silently;
- every project MCP server in `.mcp.json` starts with its committed config and answers the protocol handshake, so the browser tool is known to work in every session; a checkout without the server installed, such as the CI harness job, skips it with a printed note.

It runs as the `harness` job in `.github/workflows/ci.yml` and locally via `bash scripts/ci/assert_claude_harness.sh`. Any temporary exception would be a commented, removable entry near the top of the script, never a silent skip.

Checking the configuration's own consistency in CI goes a step beyond current vendor documentation; the harness here is large enough to drift on its own, so the check earns its keep.

Beyond this deterministic check, the `bug-hunt` skill's discrepancy lane adversarially audits the same configuration against this guide, catching what a fixed script cannot: a guard bypassable by substitution or reordering, a permission gap, or a place this guide no longer matches the configuration. The review against current Anthropic guidance, which is not static, is the `update-config` skill's harness-review mode. This guide states design rationale and is not a frozen authority; where the configuration's actual behavior and this guide disagree, the configuration is the truth for behavior and the discrepancy is a finding to resolve. The two checks are complementary; neither replaces the other.

## 13. Anti-patterns This Harness Avoids

Common failure modes in Claude Code setups, each paired with this repository's countermeasure.

- **A bloated root `CLAUDE.md`.** Subtree detail belongs in a scoped rule; rarely needed detail belongs in an on-demand document.
- **Duplicating the authority order.** Restated in several places it drifts, and a copy that ranks code above design intent inverts policy. One home, linked everywhere.
- **Routine, open-ended verification.** "Double-check this" and a standing verify-with-a-subagent step on every change cost tokens, and a reviewer asked to find gaps usually reports some even when the work is sound, which drives over-engineering. The harness delegates for breadth and for genuinely independent work, not as a routine second look. Independent judgement is kept where a false green is costly: the review skills' verifier fan-out, and the fresh reviewer the `write-tests` skill names for high-risk tests, which sees only the diff and must back every finding with a one-line break that proves it. A fresh context is used there because an author tends to choose the checks its own work already passes.
- **Done because the tests pass.** Agent-written tests can pass while the feature does not work end to end. A change a person can see is driven through the real pages on the development stack before it is called done, which is why lightweight Playwright browser-driving auto-approves, and the agent's report carries the evidence (each command run and its result) so the maintainer reviews evidence rather than re-deriving each assertion.
- **Restating a shared procedure.** A copy in several skills drifts into inconsistent versions. The deployed-surface definition lives once in the `deployed-surface` skill, cited by path; shared rules are referenced by name, never by a section number that rots.
- **A vague or over-triggering skill.** A broad description auto-fires on near-miss phrases. Explicit-only skills carry `disable-model-invocation: true`, and every skill has a precise trigger.
- **A broad mutating allow.** `Bash(sqlite3:*)` auto-approves silent writes; the repository approves `sqlite3` only through the read-only approver hook, which requires `-readonly` and refuses the shell-exec and file-write dot-command escapes, rather than any static `sqlite3` allow.
- **Over-confidence in a hook regex.** A substring match is bypassable by substitution or reordering. A static permission rule is preferred where one suffices, mirrored into `settings.json` so subagents inherit it.
- **An undocumented hook change.** Every hook ships with a fixture test and human approval; a policy change to a guard is reviewed, not quietly edited.
- **Stale memory.** Duplicates, citations of deleted documents, and one-off status accumulate silently. The write gate plus the periodic `audit-memory` pass keep the store honest.
- **A canonical document polluted with status,** or a tracker issue polluted with long-term design. The two must not blur.
- **A dated status journal inside a skill body.** It reloads into context on every invocation. Status goes in the private tracker; the skill keeps only timeless procedure.

## 14. Companion Repositories

The project spans up to three repositories, and a contributor may have any subset wired. This
section records what still works when a companion repo is absent, so a volunteer developer or an
IFPA board member can use the harness efficiently from day one.

**The repositories.**

- **footbag-platform** (this repo) — the public application: code, schema, infrastructure, tests,
  and the canonical design docs. Development, the full test suite, and architecture orientation
  need nothing else. **Operations do:** every environment's Terraform values file lives in the
  private repo and is reached from here through a symlink, so no environment is applied without
  it, and a deploy that runs the full member load refuses without it. A dev-and-tester's staging
  deploys, including a rebuild from the public inputs alone, need none of it. So "works standalone" is true of the developer and tester path and false
  of the operator path, which is a distinction worth keeping straight because a new operator who
  reads the first half stops looking for the second.
- **The private operations repo** — the maintainers' work tracker (GitHub Issues), operations
  docs, and private/sensitive data, kept private for member-data privacy. Reached through a
  canonical-named, gitignored symlink (`footbag_private_repo`) at this repo's root, plus a
  machine-local slug in `.claude/settings.local.json`. Optional for a developer or
  dev-and-tester, staging deploys included; **hard-required for applying infrastructure and for
  the full data load**.
- **The private bug-intake repository** — where developers and testers file bug reports,
  through its GitHub form or the `file-bug` skill, and where the maintainer triages them with
  the `triage-bugs` skill. Reached through the gitignored `footbag_dev_tester_repo` symlink,
  which `scripts/setup-dev-workstation.sh` makes, cloning it beside this checkout when GitHub
  admits the machine. The skills read its README, the single home for how to report a bug, and
  its forms through the link. Claude may edit the clone's files when the maintainer asks; the
  git-mutation guard keeps every commit and push there the maintainer's. Its slug, `FOOTBAG_DEVTESTER_REPO`, is set in the committed
  `.claude/settings.json`, since every developer needs the same value and it reveals nothing.
  Optional: a contributor who is not invited works without it.
- **The legacy footbag.org clone** — a read-only clone of the legacy webmaster's repository,
  reached through the `footbag_legacy_repo` symlink, beside an untouched copy of the first
  delivery (`footbag_legacy_repo_original_data`). The legacy refresh reads both. Optional per machine.
- **The footbag.org mirror crawl output** — the gitignored data tree the mirror crawler produces,
  reached through the `footbag_legacy_mirror` symlink. A data companion (not a repository),
  produced locally by the crawler or transferred maintainer-to-maintainer. Optional per machine.

**Companion governance lives in this public harness.** The companion repos are reached by
fixed-name symlinks under this repo's root, so tooling refers to them identically on every
machine while only the symlink's target stays machine-local. The private checkout has one standard
place, a sibling clone named `footbag-ops`, which the setup script defaults to. The committed
settings name that sibling as well as the symlink as working directories, because Claude Code
checks an edit through a symlink against both the link and the real file, and allows it only when
both are covered. A private checkout anywhere else still works for Terraform, but every Claude edit
into it prompts. Their governance — how to touch the
files, how the tracker is read — lives here (`.claude/rules/private-repo.md`, the `tracker-ops`
skill, and `legacy_data/CLAUDE.md`), never in a companion's own `CLAUDE.md`: a directory added
with `permissions.additionalDirectories` does not auto-load its `CLAUDE.md`/rules (only `--add-dir`
with an env-var opt-in does), so the main repo is the reliable home however a companion is reached.

**Graceful degradation is the contract.** No skill hard-fails when a companion repo is absent.
When a piece of wiring is missing, a skill says exactly one line naming the wiring step, skips the
part that needs it, and continues everything else: a tracker read with no wiring proceeds on the
human's instruction as given; a legacy-pipeline step with no legacy clone is simply skipped. This
is "solve, don't defer" — the absence is handled explicitly, never left to improvisation.

**Where to get wired.** A maintainer sets up both companion repos following the private repo's
`ONBOARDING.md` (private GitHub repo), the entry point for every private-access role: developers,
governance browser users and operators, the last continuing into the joining chapter of
`DEVOPS_GUIDE.md` (private GitHub repo). A dev-and-tester needs neither; their steps are in
`DEV_ONBOARDING.md`, "Staging as a dev-and-tester". This public guide does not restate those steps; it
records only which companion repos a given kind of work requires and how the harness behaves
without them: optional for a developer or tester, hard-required for an operator.
